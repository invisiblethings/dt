# Technical SEO Findings — proline-roofing.com

**Category Score: 61/100**

Scope tested: homepage, sitemap index + 4 sub-sitemaps, robots.txt, 3 service pages, 7 location pages, 2 blog/guide posts, 5 suspected orphan PPC landing pages, and host-canonicalization variants (www/non-www). 29 URLs fetched directly (headers + HTML); 23 rendered via headless-browser check to confirm non-SPA/server-rendered status.

**Known data limitation:** No Google API credentials are configured, so CrUX field data for Core Web Vitals is unavailable. A local Lighthouse run against the homepage also failed in this sandbox (`CHROME_INTERSTITIAL_ERROR` — the sandboxed headless Chrome would not complete navigation, unrelated to the live site). Consequently the Core Web Vitals commentary below is derived entirely from **static source-level heuristics** (image loading strategy, render-blocking resources, DOM size, format choices), not measured LCP/INP/CLS numbers. Recommend re-running PageSpeed Insights/Lighthouse from an unrestricted environment for numeric scores.

## What Works

- **robots.txt is clean and correct**: only `Disallow: /wp-admin/`, with `Allow: /wp-admin/admin-ajax.php` explicitly carved out, and a valid `Sitemap:` pointer to `https://www.proline-roofing.com/sitemap_index.xml`.
- **Sitemap structure is valid**: `sitemap_index.xml` correctly lists 4 well-formed sub-sitemaps (post-sitemap.xml, page-sitemap.xml, category-sitemap.xml, local-sitemap.xml), all returning HTTP 200 with valid XML and `lastmod` timestamps, generated by Rank Math.
- **No broken pages or redirect chains found** in the sample — all 29 tested URLs (including both sitemap-listed pages and the 5 suspected orphan LPs) returned clean HTTP 200 with zero hops.
- **Canonical tags are present, correct, and self-referencing** on every sampled page (absolute, HTTPS, matching the requested host/path) — e.g. `<link rel="canonical" href="https://www.proline-roofing.com/services/roof-repair/" />`.
- **Meta robots directives are consistent and correct**: every content page sampled uses `follow, index, max-snippet:-1, max-video-preview:-1, max-image-preview:large` (Rank Math default) — no accidental `noindex` found on any live content page.
- **Host canonicalization partially confirmed**: `https://proline-roofing.com/` (non-www, HTTPS) correctly 301-redirects to `https://www.proline-roofing.com/`.
- **Mobile viewport tag is universal**: `<meta name="viewport" content="width=device-width, initial-scale=1">` present and identical across every one of the 29+ pages checked — no gaps found.
- **Mobile navigation pattern present**: Elementor's `elementor-menu-toggle` (hamburger menu) markup is in the homepage HTML.
- **Images generally carry explicit width/height attributes** on the homepage (0 of the sampled `<img>` tags were missing dimensions) — this reduces CLS risk from image loading.
- **Server-side rendered, not a JS-dependent SPA**: all 23 rendered pages returned `is_spa: False` with full content present in raw HTML — no risk of content being invisible to crawlers that don't execute JavaScript.
- **Some render-blocking mitigation already in place**: homepage loads its main stylesheet via a `rel="preload" ... onload="this.rel='stylesheet'"` swap technique (LiteSpeed Cache optimization) rather than a blocking `<link rel="stylesheet">`.

## Findings

### 1. Two orphan PPC landing pages are near-duplicate, thin, and indexable — direct keyword cannibalization
**Severity: Critical**

`/roofer-old-bridge-nj/` and `/roofing-services-nj/` are templated PPC-style landing pages that extract to only **65–66 words of unique body copy each** (vs. 1,189 words on the proper `/locations/new-jersey/old-bridge/` page). Their meta descriptions are **byte-for-byte identical**: `"Expert repairs, quality roof replacements, honest advice. Get a free, no-pressure estimate today."` Their body copy differs only by a single token (`Old Bridge, NJ` vs. `New jersey`) inside an otherwise identical template: `"#1 TRUSTED, RELIABLE, {location} ROOFER 🇺🇸 / Roofs that protect, endure, and inspire. / Expert repairs, quality roof replacements, honest advice..."`. Both pages are:
- Self-canonical (`<link rel="canonical" href="https://www.proline-roofing.com/roofer-old-bridge-nj/" />` and `.../roofing-services-nj/` respectively) — canonicalization does **not** consolidate them into the proper location/service pages.
- `robots: follow, index` — fully indexable.
- Present in `page-sitemap.xml` — Google is being actively directed to crawl and index this thin duplicate content.
- Not linked from the homepage or main navigation (confirmed via `href` scan of homepage HTML) — i.e., orphaned pages that only exist for external (PPC) traffic but are nonetheless exposed to organic crawling/indexing.

This directly cannibalizes the keyword targets of `/locations/new-jersey/old-bridge/` ("Old Bridge, NJ Roofer | Repair & Replacement") and the NJ services/location hub, and risks Google choosing the thin page as canonical or filtering both as duplicates.

**Recommendation:** Add `<meta name="robots" content="noindex, follow">` to both PPC landing pages (or, better, set their canonical tag to point at the real target page — `/locations/new-jersey/old-bridge/` and `/services/` or `/locations/new-jersey/` respectively) and remove them from `page-sitemap.xml` (exclude via Rank Math's sitemap post/page exclusion setting). Keep them live for paid-traffic conversion purposes, just out of the organic index.

### 2. Zero security response headers site-wide
**Severity: High**

Checked response headers on 29 URLs (homepage, all sitemaps, service pages, location pages, blog posts, orphan LPs) — **none** returned `Strict-Transport-Security`, `X-Content-Type-Options`, `Content-Security-Policy`, `X-Frame-Options`, or `Referrer-Policy`. Full header set observed on the homepage:
```
accept-ch, permissions-policy (Client Hints only), content-type, link, vary,
server: LiteSpeed, alt-svc, x-litespeed-cache, content-encoding, content-length, date, connection
```
No security headers of any kind are present. This is a server/CDN-level gap (LiteSpeed) unrelated to Rank Math/Elementor, but it affects clickjacking protection, MIME-sniffing protection, and forces browsers to rely on redirect behavior alone for HTTPS enforcement.

**Recommendation:** Add via LiteSpeed server config, `.htaccess`, or a security-headers plugin: `Strict-Transport-Security: max-age=31536000; includeSubDomains; preload`, `X-Content-Type-Options: nosniff`, `X-Frame-Options: SAMEORIGIN` (or a `frame-ancestors` CSP directive), and a baseline `Content-Security-Policy`. Verify with securityheaders.com after deployment.

### 3. Sitewide "Product" + fake review schema injected on every page type, including non-commercial pages
**Severity: High**

Every page sampled — including `/faq/`, `/contact/`, `/privacy-policy/`-adjacent legal pages, and all location pages — carries an identical JSON-LD block:
```json
{
  "@context": "https://schema.org/",
  "@type": "Product",
  "name": "Contractor",
  "brand": {"@type": "Organization", "name": "ProLine Roofing"},
  "aggregateRating": {"@type": "AggregateRating", "ratingValue": "4.9", "bestRating": "5", "worstRating": "1", "reviewCount": "97"}
}
```
Using `Product`/`AggregateRating` markup on pages that are not product pages (FAQ, Contact, location landing pages, legal pages) violates Google's structured data content guidelines for review/rating rich results and risks either the rich result being silently suppressed or a manual action for spammy structured markup.

**Recommendation:** Replace this sitewide default with `LocalBusiness`/`RoofingContractor` schema (with `aggregateRating` nested under the business entity, not a generic "Product" named "Contractor"), scoped only to pages where it's contextually appropriate (homepage, About, location pages, Contact). Remove it entirely from FAQ, legal, and blog content pages. This is very likely a Rank Math "default schema type" misconfiguration — check Rank Math > Titles & Meta > global schema template.

### 4. Local/Multi-location structured data is inconsistent across location pages
**Severity: High**

Of the 6 location pages checked, only `/locations/brooklyn-ny/` carries full local-business markup (`RoofingContractor`, `GeoCoordinates`, `PostalAddress`, `OpeningHoursSpecification`, `Place`). The `/locations/` hub, `/locations/new-jersey/old-bridge/`, `/locations/new-jersey/roof-repair/`, and `/locations/staten-island-ny/roof-repair/` all lack any `RoofingContractor`/`LocalBusiness`/geo schema — they only carry the generic sitewide `Product`+`AggregateRating`+`BreadcrumbList` block described in Finding 3. For a multi-location Local Service Business (Staten Island HQ + Brooklyn + 6 NJ towns), consistent per-location `LocalBusiness`/`Service`+`areaServed` schema is a meaningful local-pack/map-pack ranking and rich-result signal that is currently only implemented for one of seven location URLs.

**Recommendation:** Apply the same `RoofingContractor`/`LocalBusiness` + `GeoCoordinates` + `areaServed` template used on `/locations/brooklyn-ny/` to every location page (NJ towns and Staten Island), ideally dynamically via Rank Math's location variables or a custom Elementor dynamic-tag/schema module so future location pages inherit it automatically.

### 5. Additional orphan PPC landing pages create duplicate-content and crawl-budget risk against the real money pages
**Severity: High**

`/brooklyn-roofing-lp/`, `/affordable-roofing-in-brooklyn-ny/`, and `/asphalt-shingle-roofing-staten-island/` (plus the two thin pages in Finding 1) are all: indexable, self-canonical, present in the sitemaps (the first two in `page-sitemap.xml`, `asphalt-shingle-roofing-staten-island` and `affordable-roofing-in-brooklyn-ny` in `post-sitemap.xml`), and **not linked from the homepage nav** — confirming they sit outside the site's normal information architecture (consistent with being PPC-only landing pages that were never `noindex`ed). Unlike Finding 1, these three do have substantial unique content (900–1,600 words each), so they are not literally duplicate text, but they directly target the same head terms as existing indexed pages:
- `/brooklyn-roofing-lp/` and `/affordable-roofing-in-brooklyn-ny/` both compete with `/locations/brooklyn-ny/` for "Brooklyn roofing/roofer" intent.
- `/asphalt-shingle-roofing-staten-island/` competes with `/services/residential-roofing/asphalt-shingle-roofing/` for "asphalt shingle roofing" intent.

With 5 total orphan LPs sitting in the sitemaps alongside the 49 "real" pages, roughly 10% of the sitemap's page entries are PPC-only pages with no internal links pointing to them — a crawl-budget and topical-authority dilution issue on a 74-URL site, and a likely source of keyword cannibalization in rankings/GSC query reports.

**Recommendation:** Decide whether each orphan LP is still an active ad destination. For active ones, keep them live but set `noindex, follow` (Google Ads does not require indexability) and drop them from the sitemap. For retired ones, 301-redirect to the equivalent `/locations/` or `/services/` page. Either path removes the cannibalization/crawl-budget issue while preserving PPC landing-page functionality.

### 6. Likely LCP-risk image-loading pattern and low modern-format adoption
**Severity: Medium**

Source inspection of the homepage (no CrUX/Lighthouse data available — see limitation note above) shows all images, including what appears to be the above-the-fold hero/content image, are delivered via a JS-based lazy-load pattern: a base64 SVG/GIF placeholder in `src` with the real image deferred to `data-src` (e.g. `<img data-lazyloaded="1" src="data:image/gif;base64,..." data-src="https://www.proline-roofing.com/wp-content/uploads/2024/04/qn-t-py17vc-768x526.jpg" ...>`), rather than native `loading="lazy"`/eager attributes. If this pattern is applied to the actual LCP element, the browser cannot discover and start fetching it from the initial HTML parse, which is a known LCP-delay anti-pattern. Separately, `fetchpriority="high"` was found on only one image site-wide — a secondary "Ratings" trust-badge graphic — not on what is likely the true hero content image, meaning the priority hint may be pointing the browser at the wrong resource. Only 6 `.webp` references were found across the homepage's ~21 `<img>` tags; the rest are legacy PNG/JPG.

**Recommendation:** Audit the actual LCP element per page (via Lighthouse/PageSpeed once available) and ensure it (a) is NOT behind JS-based lazy-loading, (b) carries `fetchpriority="high"` and a `<link rel="preload" as="image">` hint instead of the trust-badge image, and (c) is served in WebP/AVIF with responsive `srcset`. This is likely controlled by the LiteSpeed Cache "Lazy Load Images" setting — exclude the LCP hero image via its image exclusion list.

### 7. Inconsistent location-page URL taxonomy
**Severity: Medium**

The 6 NJ towns are nested under a state-level path — `/locations/new-jersey/{clifton,elizabeth,freehold,jersey-city-nj,newark,old-bridge}/` — but Brooklyn (also served, also technically in NY) sits directly at `/locations/brooklyn-ny/` with no `/locations/new-york/` parent, and Staten Island uses yet a third pattern, `/locations/staten-island-ny/roof-repair/` (service nested directly under a city slug with no bare city page at all — there is no `/locations/staten-island-ny/` overview URL in the crawl). Additionally, `/locations/new-jersey/jersey-city-nj/` carries a redundant `-nj` suffix that none of its 5 NJ sibling slugs use (`clifton`, `elizabeth`, `freehold`, `newark`, `old-bridge`).

**Recommendation:** Standardize on one hierarchy pattern, e.g. `/locations/{state}/{city}/` for all seven locations (add a `/locations/new-york/brooklyn/` and `/locations/new-york/staten-island/` overview page), and drop the inconsistent `-nj` suffix from the Jersey City slug (with a 301 from the old URL). Consistent, predictable URL patterns simplify breadcrumbs, internal linking, and hreflang/canonical logic as more locations are added.

### 8. HTTP → HTTPS redirect could not be verified from this environment
**Severity: Info**

This sandbox's outbound proxy rejects all plain-HTTP (port 80) CONNECT attempts regardless of destination host — confirmed by testing both `http://www.proline-roofing.com/` and a known-good control (`http://example.com/`), both of which returned the proxy's own `403 host_not_allowed` response rather than any response from the origin server. This is an environment limitation, not a finding about the live site. What **was** confirmed: `https://proline-roofing.com/` (non-www HTTPS) correctly 301s to `https://www.proline-roofing.com/`.

**Recommendation:** Independently verify (via an external redirect-checker tool or `curl -I http://www.proline-roofing.com/` from an unrestricted network) that plain-HTTP requests 301-redirect to HTTPS on the canonical www host, and add an HSTS header (see Finding 2) once confirmed.

### 9. No IndexNow implementation detected
**Severity: Low**

Checked `/indexnow.txt` and `/.well-known/indexnow.txt` — both returned 404 (WordPress's standard "not found" page, not a custom key file). No evidence of IndexNow key registration was found, meaning content updates aren't being pushed proactively to Bing/Yandex/Naver; those engines rely solely on their own crawl schedules against the Rank Math sitemap.

**Recommendation:** Install an IndexNow-compatible plugin (e.g., "IndexNow" or Rank Math's built-in Bing/IndexNow integration if on a supporting version/tier) and submit the key file so new/updated posts and location pages are pushed to Bing/Yandex immediately, rather than waiting for their next crawl.

### 10. Thin hub pages
**Severity: Low**

`/locations/` and `/services/` — the two primary hub pages a multi-location, multi-service business would want to rank for broad "roofing services" / "service area" queries — extract to only ~71 and ~58 words of unique body text respectively beyond their navigational cards. They are correctly indexable and canonical, but offer little unique on-page copy for topical relevance signals.

**Recommendation:** Add 150–300 words of unique intro copy to each hub page summarizing the service/location breadth (with internal links already present via the card grid retained), improving both user context and topical depth for these high-value navigational pages.

### 11. Core Web Vitals field and lab data both unavailable in this audit
**Severity: Info**

No Google API credentials are configured (confirmed via `google_auth.py --check`), so CrUX field data could not be pulled. A local Lighthouse attempt against the homepage also failed with `CHROME_INTERSTITIAL_ERROR` (the sandboxed headless browser could not complete navigation — an environment/certificate constraint, not a site outage, since the same URL was independently fetched successfully via plain HTTP requests moments earlier). All Core Web Vitals commentary in this report (Finding 6) is therefore based on static HTML source inspection only, per the audit brief's fallback guidance.

**Recommendation:** Run PageSpeed Insights (web.dev/measure or the API) and/or Lighthouse from a network environment with full Chrome/Google API access to get numeric LCP/INP/CLS scores per template (home, service, location, blog), then re-prioritize Finding 6 based on actual measured values.

### 12. No AI-crawler-specific robots.txt directives
**Severity: Info**

robots.txt currently allows all user-agents except `/wp-admin/`, meaning known AI crawlers (GPTBot, ClaudeBot, PerplexityBot, Google-Extended, Bytespider, etc.) are implicitly allowed. This is a reasonable default for a local-service business seeking AI-search visibility/citations, not a defect — flagged here purely as a decision point.

**Recommendation:** No action required unless the business wants to opt out of AI model training (e.g., blocking `GPTBot`/`Bytespider` specifically) while still allowing `ChatGPT-User`/`PerplexityBot` real-time browsing citations. Revisit if an explicit AI-visibility strategy is defined (see `seo-geo` skill).
